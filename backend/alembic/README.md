# Alembic Migrations

Source of truth for database schema evolution.

## Quick reference

```bash
# Apply all pending migrations
make db-migrate

# Generate a new migration from model changes
make db-revision m="add user preferences column"

# Roll back the most recent migration
make db-rollback

# Mark the current DB as already at head without running migrations
# (used once when transitioning a legacy DB that was created via init_db)
cd backend && alembic stamp head
```

## Conventions

- One revision per PR. Two unrelated schema changes must be two files.
- File names: `NNNN_short_slug.py` (four digits, zero-padded).
- Always review autogenerated migrations. Alembic cannot always detect
  column renames or column type narrowing — if you see `drop_column` +
  `add_column` for what should be a rename, fix it manually with
  `op.alter_column(..., new_column_name=...)`.
- Always implement `downgrade()`. If a change is truly irreversible, make
  that explicit with `raise NotImplementedError("irreversible")`.
- Enable `compare_type=True` and `compare_server_default=True` in `env.py`
  so type / default drift is detected.

## Transitioning a legacy database

If your database was created by the old `init_db()` (`Base.metadata.create_all`)
before Alembic was introduced, run this **once**:

```bash
cd backend && alembic stamp 0001_baseline
```

This records the baseline without trying to re-create existing tables. Future
migrations will apply on top.

## SQLite vs PostgreSQL

Tests run against SQLite via `conftest.py`. `app.db.session.init_db()` still
calls `Base.metadata.create_all()` for SQLite because it is cheaper and avoids
spinning up alembic for every unit test. PostgreSQL production / dev
environments go through alembic exclusively.
